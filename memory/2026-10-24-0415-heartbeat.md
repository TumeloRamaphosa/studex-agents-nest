**Scope, stated precisely:** the log FILE is `-rw-r--r--` but its DIRECTORY is

**root-level** process, not to the internet. That is materially smaller than the
public-repo GoDaddy/Blotato exposure, and it is now closed. Recording it as a
"public leak" would be false; recording it as nothing would be false too.

Redacted **in place** with a same-length mask. This is the only safe method for
a file a running process holds open for append:
- `mv`/`rename()` swaps the **inode** → the gateway keeps writing to the
  orphaned original and the visible log silently freezes. Looks fixed; isn't.
- truncating destroys the diagnostic trail for no disk gain (15G free).
- overwriting bytes in place keeps offsets, inode, fd and append position valid.

Verified after: size unchanged · inode unchanged (318874) · **0 live literals
remain** · all 113 sampled lines still parse as JSON · gateway HTTP 200.

**Two deliberate non-actions.** The active log is *not* truncated or replaced.

### The liveness lesson (again, in a new costume)
My first audit script labelled any key "LIVE" if the string was in `.env`. But
`am_us_057fa6...` is in `.env` and returns **HTTP 403** — a known-dead key. So
"present in .env" ≠ "live", and that script overstated the exposure (it counted
the 403 key as live in 3 files). The final script asks the **provider**:
probe each key, mask only what answers 200. **Dead keys are not masked** — the
point is removing a usable secret, not reducing a count.

Lesson: *a credential's presence in a file is not its liveness.* The same trap
that made a 401 read as "the key is dead" has now appeared in the opposite
direction, and it would have made me redact dead values and call it a win.

And the mirror: *the file's permissions are part of the exposure.* The log
file itself is world-readable, but its parent directory is not, so the real
blast radius was root-only. A finding quoted without its path is a finding
quoted without its scope.

Also verified: `/tmp/studex-scrub` (the concurrent session's 1.4G clone) holds
**no live keys** in its working tree — the only `am_us_` strings in it are
`am_us_dead_key_0/1/2` fixtures, identical to ours.
