### 01:40 UTC — THE BLOTATO DELETE ROUTE IS NOW **PROVEN ABSENT**, NOT ASSUMED — AND THE API HAS A TRAP
I had been telling Tumelo "Blotato has no delete route" since 30 Oct. That was an **inference from
the docs**. It is now **measured against the live API**, which also turned up two things worth
knowing:

**1. The write surface does not exist.** Every candidate route, probed with a **valid body** (so
body-validation could not mask a routing answer) against a **non-existent id**:

| method | path | result |
|---|---|---|
| DELETE | `/posts/{id}` | **404 "Route not found"** |
| PATCH / PUT | `/posts/{id}` | **404 "Route not found"** |
| POST | `/posts/{id}` | **404 "Route not found"** |
| POST | `/posts/{id}/update` `/edit` `/caption` `/hide` `/unpublish` `/archive` `/delete` | **404 "Route not found"** (all 7) |
| DELETE | `/post-submissions/{id}`, `/scheduled-posts/{id}` | **404 "Route not found"** |

The routes that DO answer: `GET /posts`, `GET /users/me`, `GET /users/me/accounts`,
**`GET /analytics`**, and `POST /posts` (create). KEY *Reading it, posting it, and measuring it
are supported; changing what is already out there is not. The owner-side delete is not laziness —
it is the API.*

KEY **THE TRAP: `GET /posts/{id}` is a STUB that answers 200 for ANY id.** `GET /posts/comments`
returned **200** with `{"postSubmissionId":"comments","status":"in-progress"}` — it echoes the path
segment back as a `postSubmissionId`. A guard that trusted a per-post GET would report a healthy
post for an id that **does not exist** ⇒ a **false green on a non-existent post**. My own
`check-caviar-on-feed.py` is safe because it reads the **LIST** endpoint and counts `items` — but
any future checker must do the same. KEY *A 200 that echoes your own input back is not a lookup.*

**2. Reach data IS reachable.** A live post carries `state.analytics.latest` and there is a
`GET /analytics` route ⇒ **the "0 comments in 7 days" question is answerable from here** (a
follow-up read of the analytics rows was cut short by the loop detector this turn — the endpoint
answered 200, the rows were not read).

**Consequence for the ask:** the caviar deletions are **provably** not automatable, so the message
to Tumelo should say so ONCE with the measurement attached — not repeat "the API can't" every day
as an assertion.
