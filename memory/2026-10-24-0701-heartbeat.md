## 1. TOOLS.md is injected into the agent's context

`TOOLS.md` and `TOOLS_SUPPLEMENT.md` are loaded into the agent's context on
**every session**, and agent output is captured into the gateway session log.
A credential in either file sits on the path:

    secret → context → log → possibly a Discord message or a commit

That is exactly how live AgentMail keys reached `/tmp/openclaw/*.log` earlier
in the week. Both files are untracked, so they were never *published* — but
`/workspace` files are externally accessible on this platform, so untracked is
not private.

**The contract now:** these files name the VARIABLE; the value lives in
`/workspace/.env` (untracked, gitignored).

`ops/repair-doc-credential-pointers.py` enforces it and
`ops/test-doc-credential-pointers.py` (14 assertions) proves it:
- fails on a real credential literal
- fails on a pointer that does not resolve in `.env`
- repairs a literal `.env` holds into a pointer
- is idempotent
- does **not** mangle the many things that are credential-*shaped* but are not
  credentials — Drive folder ids, an IP, an endpoint, a VM id, a Meta app id

### The lesson that cost the most

**A pointer that resolves to the WRONG secret is worse than no pointer,
because it looks right.**

The first version of the tool derived a variable NAME from the line's label
and pointed the doc at whatever `.env` held under that name. That produced:
- Alibaba's "Access Key Secret" pointing at `ALIBABA_ACCESS_KEY_ID`
- a Drive folder id rewritten into a token pointer
- the Facebook user and page tokens swapped
- a revoked Daytona key renamed to the live one
- `ALIBABA_SSH_PASSWORD` holding a Drive folder id
- Tencent and Orgo NEW swapped
- `FACEBOOK_USER_TOKEN` holding the Facebook **page id**

A later version assigned names **positionally**, which is the same mistake
in a new costume. The final version matches by **EXACT VALUE** against
`.env`, or reports and fails. It never infers a name from position.

### `config/mcporter.json` needed a different fix

The file has to **work**, so the credential cannot simply be deleted.
mcporter merges the untracked system config (`/root/.mcporter/mcporter.json`,
root-only) with the project config, and **a server declared in the project
config overrides the system entry for that server** — so a bare entry without
the `Authorization` header does *not* fall through, it drops to OAuth and
stops working. Measured:

    with the header in the tracked file   -> 40-tool schema, auth OK
    with `${HONCHO_API_KEY}` in it        -> "Environment variable(s)
                                             HONCHO_API_KEY must be set"
    with the server REMOVED from it       -> 40-tool schema, auth OK

So the credential-bearing servers now live **only** in the untracked system
config and the tracked file keeps the credential-free ones. Verified: mcporter
lists all five servers; honcho returns its 40-tool schema; blotato its 35.
Composio still reports `auth required` and still needs `mcporter auth
composio` — it did before the change too, because the Bearer header was never
what authenticated it.

Documented in `config/mcporter-NOTES.md`.
