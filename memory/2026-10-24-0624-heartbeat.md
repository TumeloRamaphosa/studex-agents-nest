### A FALSE POSITIVE IN THE UNTRACKED-FILE HYGIENE CHECKER — and its cause
The first run of `ops/heartbeat-verify-report.py` flagged **two** untracked files as
`CONTAINS A REAL CREDENTIAL`:
`memory/2026-10-24-0557-heartbeat.md` and `ops/restore-doc-pointers-2.py`.
A second run, minutes later, reported **both clean** — with **no edit to either file**
(`restore-doc-pointers-2.py` mtime unchanged, and its only match was the *env-var name*
`TYPESTACK_API_KEY_FROM_DOCS` whose **value is the literal string `TYPESTACK_API_KEY`**).

🔑 **The root cause is a value that is itself a variable name.** `/workspace/.env` carries
`TYPESTACK_API_KEY_FROM_DOCS=TYPESTACK_API_KEY` — a pointer, not a secret. Any file that
merely *mentions* `TYPESTACK_API_KEY` therefore matches it byte-for-byte, and the checker
reports a credential hit. The checker asks "does any real .env value appear here?" and a
**pointer value answers yes to any mention of the name**.
🔑 **A presence check against values cannot distinguish a secret from a label.** The fix
belongs in the data, not the checker: a `.env` value that is *literally the name of another
variable* is a pointer and must be excluded (or flagged as `POINTER, not a secret`) before
the value set is built. Until then, treat "CONTAINS A REAL CREDENTIAL" on a file that only
*names* variables as a false positive — **verify by opening the match before acting.**
(And note: the second run disagreed with the first on identical files, so **a hygiene
verdict that flips without a file change is itself a signal** — read the match, don't trust
the label.)
