### 06:21 UTC — THE PASS COULD NOT SEE THAT THE PASS DID NOT RUN, AND NOW IT CAN

**The gap.** On 2026-10-30 the 03:23Z and 04:23Z canonical-pass slots never ran: both cron turns died of an upstream API rate limit after ~24 seconds, before the runner was ever invoked. No log file, no state key, no memory note, and `delivered: false` meant nothing reached Discord either. The 05:23 pass found the gap by reading the cron list **by hand**.

**Why no checker could see it.** `cron-times` asks "did the job FIRE when its name promises?" — it fired on time and *then* died. `cron-kills` asks "was the last run killed by its own TIMEOUT budget?" — these runs were killed by a provider, not a timeout. Every other checker reads the state of the WORLD (live pages, feeds, credentials). **Not one of them read whether the pass itself ran.** A guard that watches the world cannot see the watcher stop.

**The guard: `ops/check-pass-completion.py`** (registered `pass-completion` — the 23rd checker).
For every scheduled slot in a 6-hour window it asks ONE question: *is there evidence the runner reached its VERDICT line?* Evidence is the pass log containing a column-0 `VERDICT`, the pass-record JSON, or a `pass_<hhmm>_YYYY_MM_DD` state key. A slot that is still owed but produced nothing is a FINDING. A slot whose log exists but never printed a VERDICT is an INCOMPLETE pass — it started and died mid-run, so it proved nothing.

**Negative controls (the part that matters).** A missing slot is a PERMANENT hole in the log, so an unbounded rule would re-announce a two-hour-old gap for ever and every later pass would cry wolf. The controls prove the rule does NOT fire for: the slot the pass is currently inside (30-minute grace), slots from before the pass was a cron job at all (the job's own creation time), an aged-out gap (6-hour window), a disabled job, and a schedule that is not hourly. `ops/test-pass-completion.py` — 20 checks, all pass; registry test 115/115; runner-contract test 68/68.
